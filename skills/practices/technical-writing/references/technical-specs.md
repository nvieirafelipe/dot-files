# Technical specs and design proposals

Write for the people evaluating or implementing the proposal. Use their existing
template. Include the sections they need to make the decision; a small change
may need only a few paragraphs.

Start with the problem, who it affects, and the proposed solution. Distinguish
current behavior from intended behavior. State requirements and assumptions, and
identify unresolved questions. Keep scope exclusions brief.

Explain affected interfaces and data, dependencies, important flows, failure
cases, and recovery. Include alternatives and reasons for the recommendation
when there is a meaningful choice.

Address testing, success measures, monitoring, deployment, and rollback where
relevant. State which work must happen first. Include owners, dates, estimates,
and approvals only when supplied or verified.

For each open question, identify the decision that depends on its answer. Keep
agreed decisions, proposals, and missing evidence distinct. A written proposal
is not an approved design.

Check that a reviewer can assess the assumptions, compare options, and
understand how success will be measured. Read the draft as if you had to implement
the design from the spec alone, and fill the gaps that reading exposes. Remove empty
headings and unrelated checklist sections. Update the spec when implementation
changes the design.

Based on the
[Stack Overflow guide to technical specs][specs].
