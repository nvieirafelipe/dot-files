# Testing — Personal Elixir

ExUnit + Mox/Mimic. Async by default; if not, comment why.

## Contents
- File layout and aliases
- Describe/test naming
- Assertion: full-struct equality, never per-field
- Pattern matching in assertions — when allowed

- Factories — never call production code in setup

## File layout and aliases

- One test file per module: `MyApp.Foo` ↔ `test/my_app/foo_test.exs`.
- Alias the module under test as `Subject`. Always call `Subject.func`, never the long name.
- Blank line after the `Subject` alias, before the rest of the aliases. Visually separates the subject from incidental dependencies.

```elixir
alias MyApp.Core.Foo, as: Subject

alias MyApp.Core.Test.Factory
alias MyApp.Core.Test.Mocks
alias MyApp.Entity
```

## Describe/test naming

- One `describe` per `function/arity`, e.g. `describe "build/4"`. The function name belongs in the describe, never in the test name.
- Test name takes exactly one of two forms:
  - **Behavior form** (happy path / only path): `test "<verb phrase>"` — third person, present tense, starts with a verb. Examples: `test "returns the currency rate"`, `test "persists the row with inserted_at from the clock"`.
  - **Conditional form** (branching on input or state): `test "when <condition>, <result>"` — comma separates condition from result. The "when" clause lives in the test name, never in the describe. Examples: `test "when tax rules are applied, returns prices with taxes"`, `test "when the file is missing, returns a file_not_found error"`.
- Never embed the function name in the test name — the describe carries it. Avoid `test "list_expenses/0 returns all expenses"`; prefer `describe "list_expenses/0"` + `test "returns all expenses"`.
- Never put "when" at the end of the test name. The condition always comes first. Avoid `test "returns 401 when not logged in"`; prefer `test "when not logged in, returns 401"`.
- Never use "should". Direct statements only. Avoid `test "should return the user"`; prefer `test "returns the user"`.
- One assertion per `test` block. Exceptions exist; reach for them sparingly.
- Multi-line test name: use heredoc with trailing `\` continuation. Note the 255-char ExUnit atom limit on the full test name.

Avoid:
```elixir
describe "expenses" do
  test "list_expenses/0 returns all expenses" do ...
  test "create_expense/1 with valid data creates a expense" do ...
  test "create_expense/1 with invalid data returns error changeset" do ...
  test "returns 401 when not logged in" do ...
end
```

Prefer:
```elixir
describe "list_expenses/0" do
  test "returns all expenses" do ...
end

describe "create_expense/1" do
  test "when given valid data, creates the expense" do ...
  test "when given invalid data, returns an error changeset" do ...
end

describe "show/2" do
  test "when the user is not logged in, returns 401" do ...
end
```

## Assertion — full-struct equality

Compare whole structs/maps with `==`. Never per-field assertions, never `assert {:ok, var} = result` followed by `assert var.field == ...`.

Why: a single equality check fails fast, reads cleaner, and surfaces drift on every field — not only the fields the author remembered to check. Pattern matching ignores added fields; equality flags them.

Avoid:
```elixir
assert {:ok, entity} = Subject.do_thing(args)
assert entity.field_a == expected_a
assert entity.field_b == expected_b
```

Prefer:
```elixir
expected = %Entity.Thing{field_a: a, field_b: b, field_c: c}
assert Subject.do_thing(args) == {:ok, expected}
```

For errors, build the expected error with the same builder and compare the whole `{:error, error}` tuple. Never pick apart error fields individually.

For list results: `assert items == [...]` in one shot. Never `length(items) == 2` plus per-index `Enum.at` assertions.

Function call on LEFT, expected on RIGHT:
```elixir
# Avoid
assert expected_value == Subject.my_function(param1)

# Prefer — reads as "assert that Subject.x satisfies expected"
assert Subject.my_function(param1) == expected_value
```

## Pattern matching in assertions — when allowed

Pattern matching belongs in two cases only:

1. Capturing autogenerated values (timestamps, UUIDs) so the expected struct can be built with them. Even then, follow targeted-match-then-equality:

```elixir
assert {:ok, inserted} = Subject.insert(params)

expected =
  :foo
  |> Factory.Schema.build(
    id: inserted.id,
    inserted_at: inserted.inserted_at,
    updated_at: inserted.updated_at
  )

assert inserted == expected
```

2. Asserting only on shape, not exact values: `assert {:ok, %Entity.Thing{field_a: ^a}} = Subject.do_thing(args)`.

## Fixing FactoryInTests findings — and the evasions that don't count

The `Checks.Design.FactoryInTests` Credo check flags inline map/struct literals, per-field assertions, and pattern-match assertions. The fix is always the same shape: **bind the result, build the WHOLE expected from a factory, compare with `==` / `assert_eq`.** Rewriting the assertion into something that merely silences the check while still testing one field at a time is an *evasion* — it defeats the purpose. Recognise and avoid these:

```elixir
# finding: pattern-match assertion
assert {:ok, %Account{is_default: true}} = Accounts.create(scope, attrs)

# WRONG — match?/2 just hides the pattern from the check
assert match?({:ok, %Account{is_default: true}}, Accounts.create(scope, attrs))

# WRONG — reconstructing a partial map is a per-field assertion in disguise
assert {:ok, account} = Accounts.create(scope, attrs)
assert %{is_default: account.is_default} == %{is_default: true}

# WRONG — per-field via the helper is still per-field
assert_eq account.name == "Checking"

# RIGHT — bind, build the whole expected from a factory, compare whole
assert {:ok, account} = Accounts.create(scope, attrs)
expected = Factory.account(id: account.id, is_default: true, name: "Checking")
assert_eq account == expected
```

Recurring cases and their canonical fixes:

- **Constructable error/result struct** → factory equality, never `match?`:
  `assert_eq error == Factory.error(:fx_provider_unavailable)`.
- **Non-deterministic field** (free-form `reason`, etc.) → pin it with `=~`, seed it into the expected so the rest still compares whole:
  ```elixir
  assert {:error, error} = Subject.fetch_rate("USD", "BRL", date)
  assert error.details.reason =~ "quote_not_found"
  assert_eq error == Factory.error(:fx_provider_unavailable, details: error.details)
  ```
- **"returns a changeset" shape test** → assert a real property, not the struct's mere presence:
  `assert Subject.change_account(account).valid?` (not `match?(%Ecto.Changeset{}, ...)`).
- **Changeset errors** → compare a whole errors map, never `refute changeset.valid?` alone:
  `assert errors_on(changeset) == %{name: ["can't be blank"]}`.
- **Single-use shape** (built in only ONE file) → keep it as a private helper in that test file, built with `struct(Mod, attrs)` / `Map.new(attrs)` so the assertion site is not a bare literal. Do NOT relocate it into the shared factory namespace — that adds a hop for no reuse.

## Setup callbacks

Named setups MUST return `{:ok, key: value, ...}`. Plain keyword lists or maps work in ExUnit but the tagged tuple is canonical.

```elixir
# Avoid
defp idempotency_key(_context), do: [idempotency_key: Factory.uuid()]

# Prefer
defp idempotency_key(_context), do: {:ok, idempotency_key: Factory.uuid()}
```

Order matters. Setups run in the order listed. Dependent setups must come after their prerequisites.

```elixir
setup [:stub_time, :seed_params, :expected_result, :verify_on_exit!]

defp stub_time(_context) do
  utc_now = Factory.utc_now()
  stub(TimeMock, :now, fn -> utc_now end)
  {:ok, utc_now: utc_now}
end

defp expected_result(%{utc_now: utc_now}),
  do: {:ok, expected_ttl: utc_now |> DateTime.to_unix() |> Kernel.+(86_400)}
```

Naming conventions:
- `stub_*` — Mox/Mimic stub setup.
- `expected_*` — derives deterministic expected values from already-set context. Runs AFTER the setup that seeds input.

Three-liner setups repeated across sibling test files belong in a shared private helper module.

## Factories — never use production code

Avoid calling production builders, schemas, or constructors to build fixtures, expected values, or stubbed responses. Use factories.

Why:
- Production code evolves for runtime concerns (validation, casting, side effects). Tests coupled to those choices break for unrelated reasons.
- Factories centralize test data shapes. One edit updates every call site.
- Error structs, entities, and event payloads get dedicated factory modules.

Avoid:
```elixir
expected = Entity.Booking.build(%{id: id, status: :confirmed})
expected_error = Entity.Error.build(:not_found, "Booking not found", %{})
```

Prefer:
```elixir
expected = Factory.Entity.Booking.build(:booking, id: id, status: :confirmed)
expected_error = Factory.Entity.Error.build(:error_not_found, id: id)
```

Exception: the subject under test. If the test is `FooTest` for `Foo.build/1`, calling `Foo.build/1` directly is correct.

When no factory exists for the variant needed, **add one**. Factories grow alongside the schema.

### Factory variants get named functions, not `build/2` with atom dispatch

Each variant on a sub-factory module gets its own named function. Do not collapse them into a single `build/2` clause-list dispatching on an atom tag.

```elixir
# Avoid
defmodule Tostao.Test.Factory.Currency do
  def build(variant \\ :currency, attrs \\ [])
  def build(:brl, attrs), do: ...
  def build(:usd, attrs), do: ...
  def build(:valid_params, attrs), do: ...
end

Factory.Currency.build(:brl)
Factory.Currency.build(:valid_params, code: "USDX")

# Prefer
defmodule Tostao.Test.Factory.Currency do
  @spec brl(Enumerable.t()) :: Currency.t()
  def brl(attrs \\ []), do: ...

  @spec usd(Enumerable.t()) :: Currency.t()
  def usd(attrs \\ []), do: ...

  @spec valid_params(Enumerable.t()) :: map()
  def valid_params(attrs \\ []), do: ...
end

Factory.Currency.brl()
Factory.Currency.valid_params(code: "USDX")
```

Reasons: named functions self-document at the call site, give each variant its own `@spec`, let IDEs jump to the definition, and surface the variant pool in autocomplete. Atom dispatch hides variants from the type system and the editor.

When the root `Factory` module previously had a `defdelegate ... as: :build` shim for an atom-dispatched sub-factory, drop the shim — callers reach the sub-factory directly (`Factory.Currency.brl()`). The root module stays a thin entry point for single-variant aggregates (`Factory.user/1`, `Factory.account/1`).

### Always use factories, never bare maps or struct literals

Every test input / expected value that is a map or struct must come from a factory — never an inline `%{...}` literal or `%MyModule{...}` constructed in the test body.

```elixir
# Avoid — inline bare map
detail = %{
  data: %{offer: %{token: "t"}},
  metadata: %{correlation_id: "c", idempotency_key: "i"}
}

# Prefer — factory
detail = EventsFactory.Consumer.build(:create_booking_detail)
```

Stricter than the rule above. There: "use factories instead of production builders". Here: "use factories instead of any literal map or struct" — inputs as much as expected outputs.

### Every test change — audit factory use, de-duplicate without relocating single-use shapes

Whenever writing OR changing a test, first check whether its map/struct inputs and expected
values should come from a factory (per the "always use factories" rule above). When you spot an
inline shape — a literal map/struct, OR a repeated multi-key factory override block — decide
whether to extract it into a factory using this litmus test:

- **Extract into the factory namespace ONLY IF the same byte-identical shape is built inline in 2+
  files** (genuine cross-file reuse). Create or extend a factory the callers share: thread the
  per-call varying values through attrs and default the stable parts.
- **Do NOT extract a shape built in only ONE file.** Relocating a single-use shape into the shared
  factory namespace adds indirection — the reader must jump to the factory — without buying any
  reuse. It trades local clarity for nothing. Keep single-use shapes as a private helper in the
  test file (or inline).
- **Structural parts that ALREADY come from a factory call stay as-is.** Only the genuinely
  duplicated inline remainder is a candidate.

Two hard constraints on any factory you create or change:

- **NEVER write a factory that returns a list.** A factory returns a struct or map. A list of N
  built items belongs at the call site via `build_list/2` or an explicit list of `build/2` calls.
- **NEVER call `merge_attributes` on a list.** `merge_attributes` is for structs/maps only.

Nest the new or extended factory by aggregate root (per the factory-naming rules above), and give
each **new** factory module its own file (one module per file).

**Tracking parser — extend, never fork.** When the shape is a tracking-params variant, do NOT
create a parallel held-specific tracking factory module. The tracking parser and its factory already
exist for the regular flow; **update that existing tracking factory to also accept held-booking
inputs** — add a held variant / thread the held-specific values through its attrs — so the regular
and held cases share one parser and one factory. A forked held-only namespace duplicates the
parser's knowledge of the tracking shape and drifts from the regular flow.

Worked example. Two test files both built the same tracking-params shape inline, with an identical
constant field plus a nested sub-block. Rather than fork a new held-specific tracking factory, the
**existing tracking factory** was extended to accept the held-booking inputs under one named
variant that defaults the constant field and builds the nested part from an attrs map, leaving the
varying values (ids, amounts, result tags) as overridable attrs. Both callers now call the one
shared tracking factory. Single-use shapes in the same files were deliberately left inline — no
other file built them, so extracting would only add a hop.

## Parameterized tests via module-level `for`

For required-field validation, allowed-enum tests, and any "same assertion, different value" fan-out, use a module-level `for value <- @values` comprehension and `@tag`. Each variant runs as its own ExUnit test, fails independently, and the variant shows in output.

```elixir
for field <- @required_fields do
  @tag field: field
  test "when the required #{field} is missing, returns required error",
       %{field: field, params: params} do
    invalid_params = Map.delete(params, field)
    expected_error = {field, {"can't be blank", [validation: :required]}}

    changeset = Subject.changeset(%Subject{}, invalid_params)

    refute changeset.valid?
    assert expected_error in changeset.errors
  end
end
```

One test per field, not one mega-test that deletes several fields at once.

## Mocks — return per-`@spec` values

Mocked delegated functions must return values matching the callee's `@spec`, not a generic `:ok` stub. A mock returning `:ok` for a function specced as `{:ok, Foo.t()} | {:error, term()}` hides contract breakage.

```elixir
# Avoid — spec returns {:ok, entity} but mock shortcircuits
expect(Subject.Foo, :insert, fn _params -> :ok end)

# Prefer — mock returns realistic per-spec value
expected = Factory.Entity.build(:foo)
expect(Subject.Foo, :insert, fn _params -> {:ok, expected} end)
assert Subject.insert_foo(params) == {:ok, expected}
```

## ExUnit tags — context modifiers, not definers

Use callbacks to define context. Use tags only to *modify* context for specific tests.

```elixir
# Avoid — tag is the context source
describe "a group" do
  @describetag context_variable: true

  test "x", %{context_variable: cv}, do: assert cv == true
end

# Prefer — callback defines, tag overrides
describe "a group" do
  @describetag some_tag: true

  setup context do
    {:ok, context_variable: context[:some_tag]}
  end

  test "x", %{context_variable: cv}, do: assert cv == true

  @tag some_tag: false
  test "x when false", %{context_variable: cv}, do: refute cv == true
end
```

## Doctests

Purpose: keep documentation honest. Doctests run with the suite and verify examples are runnable.

- Recommended for all public functions.
- At least one happy-path scenario per function.
- Avoid overlap with unit tests — don't pile every condition into doctests.
- Doctests are NOT unit tests. Even covered doctest scenarios must exist in the unit test suite.
- Skip the `doctest` call (but keep `## Examples` with fake values) when:
  - Function depends on injected modules requiring mocks.
  - Input/output is large and hard to maintain.

## Before writing ANY new test — pre-write gate

Run this checklist BEFORE the first `test "..."` line, not after declaring the step done. Each item is a concrete action, not a guideline to remember.

1. **Grep sibling tests in the same area** — `grep -rn "describe \"#{function_name}/" test/` and read at least one. Match its style, factory imports, setup pattern. Don't reinvent.
2. **Locate or add the factory FIRST** — if asserting on a struct shape that no existing factory produces, add the factory before writing the test body. Test code that uses an inline `%Module{...}` literal or calls `Module.build/1` directly is structurally wrong and harder to fix later.
3. **Decide the expected value upfront** — write the `expected = ...` line before the `assert` line. If you cannot construct `expected` without knowing the implementation detail, the test is asserting plumbing, not behavior — reconsider the test.
4. **Single equality assertion per test** — `assert result == expected`, not N per-field comparisons. If the temptation is to add a second `assert` on the same returned struct, it belongs in `expected`.
5. **Factory location near consumers** — the factory lives close to the tests that use it. Putting domain factories in a "shared" module "because the type lives there" forces cross-package aliases at every call site.

Skipping step 1 produces tests that re-invent local conventions. Skipping step 2 produces production-code-in-tests violations. Skipping step 3 produces per-field assertion drift. Skipping step 4 = same. Skipping step 5 = renames + relocations later.

The cost of running the checklist: ~30 seconds. The cost of skipping: a full review round of fixup commits.
